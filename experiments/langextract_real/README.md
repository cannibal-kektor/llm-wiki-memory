# Эксперимент LE-2: LangExtract на фрагменте реального юридического документа

Изолированная исследовательская проверка: справляется ли конвейер LE-1 (LangExtract **1.7.1** + одобренная частная OpenAI-совместимая модель GPT-OSS-120B) с точным фрагментом реального документа. Конвейер должен:
- извлекать дословные нормативные фрагменты;
- находить явные межпунктовые отсылки с правильным направлением и гранулярностью.

Это не реализация, не юридическое заключение и не публикация в Wiki. Эксперимент не меняет LE-1, `llm_wiki/`, `pyproject.toml`, Wiki, Git-публикацию, индексацию и Docling Graph.

**Все результаты — `legal_status: UNVERIFIED`, `review_status: REVIEW_REQUIRED`.** Ответ модели или `PIPELINE_COMPLETED` не означает смысловой или юридической корректности.

## Что в репозитории и что нет

В Git попадают только код и обезличенное описание. Реальный документ, его TXT, фрагмент, якоря и маркеры структуры (частная спецификация), чек-лист, промпты, ответы модели, журнал POST и отчёты лежат только в игнорируемом `runtime/langextract-real-exp/`. Права: каталоги 0700, файлы 0600, без перезаписи. Адрес endpoint и ID модели передаются аргументами и в код не записываются.

## Состав

| Файл | Назначение |
| --- | --- |
| `source.py` | закреплённый RTF (размер и SHA-256 из частной спецификации); преобразование LibreOffice в новом профиле с фильтром `txt:Text (encoded):UTF8`; границы фрагмента; карта строк пунктов; узкая сверка с абзацами RTF |
| `references.py` | привязка извлечений к строкам; разбор отсылок; разрешение кандидатов связей только внутри фрагмента; оценка по частному чек-листу |
| `__main__.py` | CLI `prepare` / `probe` / `run`; журнал POST; переход LE-2A → LE-2B только при проверке `PASS`. Офлайн-команды LE-3A: `evidence-prepare` / `claim-request` / `claim-check`. LE-3B.1: `claim-run` (`--replay` / `--preflight` без сети, `--live` — не запускался) |
| `evidence.py` | LE-3A: снимок, точные доказательства по смещениям, явный ContextPackage (без ввода-вывода) |
| `claims.py` | LE-3A: промпт шага Claim Construction и строгая проверка ответа (без сети и клиента модели); LE-3B.1: полный частный результат |
| `claim_run.py` | LE-3B.1: сверка запроса, тело POST, журнал POST с блокировкой, проверка оболочки ответа, файл обмена и replay |

Переиспользуется из LE-1 без изменений:
- `GuardedChatModel`: один POST на промпт, без скрытых повторов и прокси, `finish_reason=length` распознаётся как обрезка;
- транспорты `http`/`replay`;
- `_run_task`, `NetworkGuard`, очистка окружения;
- промпты и примеры `PASSAGES`/`RELATIONS`;
- `ground`, `raw_items`, `raw_vs_final`, `overlaps` из `grounding.py`.

**Не переиспользуются** `paragraphs()`, `paragraph_label`, `resolve_relations()` и оценки фикстуры LE-1. Они делят текст по `\n\n`. В TXT LibreOffice пункты и абзацы разделены одиночным `\n`, поэтому весь фрагмент оказался бы одним «абзацем 27», и текст п. 28 молча приписывался бы п. 27. Поля `paragraphs`/`paragraph_label` из `ground()` удаляются и заменяются картой строк LE-2.

## Источник и единицы

- Доказательная основа — выбранный UTF-8 TXT LibreOffice, а не байты RTF.
- Смещения — символы Unicode TXT, декодированного как `utf-8`. BOM считается символом 0; декодирование `utf-8-sig` сдвинуло бы все смещения на 1.
- Фрагмент — точный срез от начала первого пункта до начала следующего пункта, включая завершающий `\n`. `prepare` отказывает, если:
  - RTF не совпадает по размеру или SHA-256;
  - вывод не UTF-8;
  - маркеры пути (акт → глава) не уникальны как целые строки или идут не по порядку;
  - якоря неуникальны или не начинают строку;
  - номера пунктов в акте повторяются;
  - во фрагмент попал следующий пункт;
  - наблюдаемые смещения и размеры расходятся с контрольными;
  - сверка с RTF не прошла.
- Сверка с RTF намеренно узкая. Между якорями в RTF (cp1251) каждый `\par` предваряется строкой с одним нейтральным оформлением `\pard\plain…`. Любой иной управляющий элемент, группа или скрытый текст — отказ. Тексты абзацев, соединённые через `\n`, должны совпасть с фрагментом. Это не общий разбор RTF и не байтовая эквивалентность.
- **Единица — строка TXT** (`27:L1`…). Номер абзаца (`abzac`) задаётся только для пункта-перечня вида «вводная: …; …; …». Только для такого пункта «абзац N» однозначно равен строке N. Пункт из нескольких частей может адресоваться частями, а не строками, поэтому для него `abzac = null`, и ссылка «абзац N» на него разрешается не точнее `PARTIAL`.

## Разрешение отсылок LE-2B

Модель предлагает доказательство, дословную `target_reference` и `relation_type` (`EXCEPTION_TO` / `OTHER_REFERENCE`, как в LE-1). Код делает следующее:
1. Проверяет доказательство как точный диапазон. Источник определяется строками, которые этот диапазон покрывает. Если цитата встречается во фрагменте больше одного раза, атрибуция зависит от вхождения: `SOURCE_OCCURRENCE_AMBIGUOUS`.
2. Требует, чтобы `target_reference` была подстрокой доказательства, и разбирает только формы «пункте N», «абзаце <порядковое> пункта N», «абзацах <порядковое> и <порядковое> пункта N». Отсылка к статье или кодексу считается внешней. Остальное получает статус `TARGET_REFERENCE_UNPARSED`.
3. Помечает `TARGET_LESS_PRECISE_THAN_EVIDENCE` и `PARTIAL`, если в доказательстве есть абзацы, которых нет в цели модели. Отсылка «абзац 3 пункта 27» не превращается молча в «пункт 27».
4. Ищет цель только внутри фрагмента. Пункт вне фрагмента и внешний акт получают `OUT_OF_SCOPE`. Полный TXT для поиска цели не используется.

Статусы:
- `CANDIDATE_RESOLVED` — цель найдена с запрошенной гранулярностью, проблем нет. Разрешение «абзац N = строка N» явно указано в `assumptions`.
- `PARTIAL` — найдена только на уровне пункта, или атрибуция неоднозначна.
- `OUT_OF_SCOPE` — цель вне фрагмента.
- `UNRESOLVED` — доказательство не подтверждено, цели нет в доказательстве, или ссылка не разобрана.

Тип связи остаётся меткой модели. Код его не исправляет: прямая отсылка вида «subject-to пункт M» (оговорка в самом источнике) — это не `EXCEPTION_TO` от источника к M.

## Запуск

Запускать из корня репозитория интерпретатором `runtime/venvs/langextract` (`langextract==1.7.1`). Выходные каталоги должны заранее существовать в `runtime/` с правами 0700.

```bash
# 1. Офлайн-подготовка без сети (повторить в другой каталог и сравнить SHA-256 TXT).
unshare -rn runtime/venvs/langextract/bin/python -m experiments.langextract_real prepare <RTF> \
  --spec runtime/langextract-real-exp/source-spec.json --output-dir runtime/langextract-real-exp/prepare-1

# 2. До вызовов модели: частный чек-лист ожидаемых наблюдений (JSON) с хешем и временем.

# 3. Офлайн-прогоны на сконструированных replay-отчётах (не результаты модели).
unshare -rn ... run <фрагмент> --source-map <карта> --task passages --replay <stub.json> \
  --checklist <чек-лист> --le1-report <отчёт LE-1> --output-dir <каталог>

# 4. Только GET: /health, /v1/models, /slots (служебные поля), /metrics.
... probe --endpoint <частный URL /v1> --label before --output-dir runtime/langextract-real-exp/probes

# 5. LE-2A (один POST), затем, только при проверке PASS, LE-2B (один POST).
... run <фрагмент> --source-map <карта> --task passages --endpoint <URL> --model <ID> \
  --post-ledger runtime/langextract-real-exp/post-ledger.jsonl --post-cap 10 --checklist ... --le1-report ...
... run <фрагмент> --source-map <карта> --task relations --passages-report <live-отчёт LE-2A> ...
```

Журнал POST — JSONL с базовой строкой `{"kind": "baseline", "count": N}`. Перед отправкой каждого запроса туда дописывается строка `post`, поэтому тайм-аут или обрыв тоже расходуют бюджет. Если `count + 1 > --post-cap`, `run` отказывает до сети. LE-2B без `--replay` требует live-отчёт LE-2A (не replay) того же фрагмента с проверкой `PASS`. Условия `PASS`:
- вызов принят;
- сырой ответ разобран строго;
- сырые и итоговые элементы совпадают;
- все элементы `VERIFIED_EXACT_SPAN`;
- нет дублей.

Параметры зафиксированы:
- `json_object`, `max_tokens` 8192;
- `temperature` не отправляется;
- один проход, `batch_length=1`, `max_workers=1`;
- тайм-аут ≤ 300 с;
- `max_char_buffer` 4000, только один чанк: иначе отказ, чанкинг молча не включается.

Токенизатор LangExtract не включает завершающий `\n` в чанк. Вне чанка допускаются только пробельные символы; фактический интервал записывается в отчёт. Отчёт также подтверждает, что промпт идентичен LE-1: текст вопроса совпадает с чанком, а часть промпта до текста побайтно совпадает с промптом LE-1 (`--le1-report`).

## Результаты (2026-10-15)

Фрагмент — п. 27–28 Положения о Парке высоких технологий, а не п. 27–28 самого Декрета. Положение входит в новой редакции через приложение 2 к Декрету № 8 от 21.12.2017. Точные идентификаторы, хеши, якоря и все тексты хранятся только в частных отчётах.

### Источник (офлайн, без сети)

- SHA-256 RTF совпал с закреплённым, кодовая страница cp1251. LibreOffice 24.2.7.2.
- Три независимых преобразования в новых профилях под `unshare -rn` дали одинаковый TXT. Его размер (байты и символы) и смещения якорей совпали с контрольными значениями. Фрагмент: 2 871 символ, 13 строк (п. 27 — 4, п. 28 — 9). Строки п. 27, 28 и 29 уникальны в пределах Положения. Фрагмент лежит между маркерами главы 5 и главы 6.
- Узкая сверка с RTF: 13/13 абзацев совпали с фрагментом. У всех абзацев одна и та же нейтральная строка оформления.
- Особенности преобразования:
  - TXT начинается с BOM, и он входит в смещения;
  - параметр фильтра `76` подходит только для CSV: с ним выход получился однобайтным, не UTF-8, и был отвергнут;
  - фильтр `UTF8` даёт корректный результат.
- В другом месте того же Положения (вне фрагмента) п. 28 адресуется частями. Поэтому номера абзацев п. 28 не выводятся (`abzac = null`).

### Подготовка до вызовов модели

- Частный чек-лист составлен до первого POST. Его SHA-256 совпадает с записанным в отчёте, время подготовки — раньше строки `post` в журнале. В нём:
  - ожидаемые нормы по строкам (`27:L2`…`28:L9`), минимальное число частей и допустимые классы;
  - 9 ожидаемых отсылок, из них 4 обязательные `EXCEPTION_TO` от строк п. 28 к абзацам 2 и 3 п. 27;
  - 2 прямые отсылки «subject-to» от строк п. 27 к п. 28: это не `EXCEPTION_TO`;
  - 1 внешняя отсылка к кодексу;
  - 1 отсылка к абзацу пункта вне фрагмента;
  - 1 отсылка с заранее не определённым типом.
- Детерминированный разбор находит во фрагменте ровно эти 9 отсылок. Внешняя ссылка на пункт статьи кодекса не путается с одноимённым пунктом Положения.
- Офлайн-прогоны на сконструированных ответах (не модельных):
  - точная привязка; одинаковые цитаты распределяются по разным вхождениям и помечаются как зависящие от вхождения;
  - нечёткий и изменённый текст даёт `OFFSET_TEXT_MISMATCH`;
  - обрезка, битый JSON и тайм-аут останавливают конвейер;
  - огрублённая отсылка (абзац → пункт) даёт `PARTIAL` + `TARGET_LESS_PRECISE_THAN_EVIDENCE` и не засчитывается как найденная;
  - цель вне доказательства даёт `UNRESOLVED`;
  - прямая отсылка, размеченная как `EXCEPTION_TO`, видна как ошибка типа;
  - отказы бюджета, проверки перехода и подмены входа срабатывают до сети.

### LE-2A: один POST

| Параметр | Значение |
| --- | --- |
| Итог | HTTP 200, `finish_reason=stop`, 117,9 с |
| Токены | 1 605 промпта, 6 560 ответа (80 % от `max_tokens` 8192), около 21 тыс. символов рассуждения |
| Промпт | идентичен LE-1: часть до текста совпадает побайтно, текст вопроса равен чанку |
| Разбор | строгий разбор OK; сырые → итоговые: 9 → 9, ничего не потеряно |
| Привязка | **2/9 `VERIFIED_EXACT_SPAN`**, 7/9 `OFFSET_TEXT_MISMATCH` |
| Выравнивание библиотеки | `match_exact` 4, `match_fuzzy` 2, `match_lesser` 3; два «точных» по оценке библиотеки на самом деле отличаются регистром и пробелами |
| Проверка перехода | **FAIL** (`NOT_ALL_VERIFIED`), поэтому **LE-2B не запускался** |

Виды недословности (проверено сравнением с фрагментом):
1. **Склейка вводной с элементом перечня.** Для трёх элементов перечня п. 27 (`27:L2`–`L4`) модель собрала самостоятельные фразы «вводная + элемент», которых в тексте нет как непрерывного диапазона. Библиотека привязала их к диапазонам, которые начинаются во вводной и тянутся через соседние льготы (`match_fuzzy` до 706 символов) или обрываются после вводной (`match_lesser`). Растянутые диапазоны захватывают соседние элементы перечня.
2. **Изменение юридически значимых слов.** В отсылке «абзац … пункта N» модель изменила падеж слова «пункт» в двух извлечениях. Библиотека выдала усечённые диапазоны `match_lesser` (50 и 155 символов при длине текста 307 и 239).
3. **Орфографическая нормализация**: удвоенная согласная и `е` → `ё`.
4. **Регистр первой буквы и замена `\n` пробелами.** Библиотека сочла это точным совпадением.
5. **Вынос условия из цитаты.** Условная часть второй нормы `28:L1` и вводный оборот `28:L4` перенесены в атрибуты, а цитата начинается после них. Эти части не вошли ни в одну цитату. Атрибуты 4 из 9 извлечений не являются подстроками своего текста.

Покрытие (три разных показателя):
- метрика кода: строк с проверенной цитатой — 2 из 12 обязательных;
- ручная смысловая оценка, без учёта дословности: каждой обязательной строке соответствует хотя бы одно извлечение; вводная `27:L1` отдельно не извлечена (по чек-листу не обязательна);
- дословные пропуски частей предложений: условие в `28:L1` и вводный оборот `28:L4` (см. п. 5).

Классы: 6/9 допустимы по чек-листу. Все три элемента `27:L2`–`L4` размечены как `exception`, хотя это освобождения, а не исключения из другого положения. Обе подтверждённые цитаты (`28:L1`, первое предложение; `28:L9`) потеряли завершающую точку. Это допустимая граница, не ошибка.

В атрибутах `references` извлечений LE-2A (это не кандидаты LE-2B) модель изменила форму отсылки, в том числе падеж. Разбор LE-2 принимает любые окончания слова «пункт». От такой формы защищает только требование, чтобы `target_reference` была подстрокой проверенного доказательства.

Сервер (только GET, без содержимого слотов): до запуска слот 0 был свободен, слот 1 занят. Во время генерации наш запрос занимал слот 0, а слот 1 последовательно обслуживал не менее четырёх чужих задач. `/metrics` вернул 501. Время ответа получено при конкурентной нагрузке и не является замером производительности.

Бюджет: по журналу 9 из 12 POST (8 — LE-1, 1 — LE-2A). LE-2B не отправлялся.

### Вывод

**Итог для дальнейшей оценки: INCONCLUSIVE.** Это не оценка готовности к эксплуатации.

- **Базовую конфигурацию LE-1 на реальной структуре повторно без изменений не использовать.** Нормы найдены, но 7/9 цитат не дословны. Без независимой проверки библиотечные смещения выдали бы неверные, усечённые или растянутые на соседние льготы диапазоны, а 2 из них — с меткой `match_exact`. Это прямой риск для происхождения утверждений.
- Пригодность подхода LangExtract не установлена:
  - сбой объясним отсутствием в примерах LE-1 перечней «вводная: …; …» и одиночных переводов строк, но это гипотеза, не проверенная.
  - LE-2B не проверялся.
  - Наблюдение одно, на одном фрагменте.
- Сравнение только качественное. Документ и структура другие, поэтому выводов о превосходстве нет.
  - На синтетике LE-1 дал 8/8 точных цитат.
  - Docling Graph на этом документе не запускался. На синтетике у него были выдуманные якоря и перевёрнутая связь (`runtime/docling-graph-exp/`).
  - Здесь недословность тоже поймана только независимой проверкой `text[start:end] == extraction_text`. Метки выравнивания библиотеки её не показали.

### Предлагаемый следующий эксперимент (не выполнялся)

Нужно отдельное разрешение на POST. Сначала офлайн-изменения, затем один повтор LE-2A на том же фрагменте с тем же чек-листом:
- добавить вымышленный пример перечня «вводная: …; …; ….» с одиночными `\n`, где вводная и элементы извлекаются отдельными дословными диапазонами;
- явно запретить в промпте изменение регистра, орфографии, падежей и склейку несмежных частей.

LE-2B запускать только при проверке `PASS`. Новые примеры удлинят промпт и, вероятно, ответ: LE-2A уже использовал 80 % `max_tokens`. Поэтому при `finish_reason=length` останавливаться и не повышать `max_tokens` без отдельного согласования. Детерминированное «перепривязывание» недословного текста к источнику не делать: оно скрывает изменения смысла.

## LE-3A: Evidence → ContextPackage → ClaimCandidate (только офлайн)

Офлайн-расширение LE-2 от 2026-10-15. Модель не вызывалась, сеть и GET-пробы не использовались, POST: 0 (по журналу по-прежнему 9 из 12). Результаты LE-2A выше не изменены: 9 извлечений, 2 точных, 7 недословных, LE-2B NOT RUN, вердикт INCONCLUSIVE.

Это узкая экспериментальная проверка обязанностей этапов 1.3 (Evidence Resolver) и 1.4 (ContextPackage), а не конкурирующая архитектура. Контракты ниже — экспериментальные, версия `le3a-*/v1`. Доменный `ClaimCandidate` из `llm_wiki/domain.py` с одной `SupportingQuotation` не меняется.

### Почему доказательство и утверждение разделены

В LE-2A модель склеивала вводную перечня с его элементом. Получалась «цитата», которой нет в тексте как непрерывного диапазона. Нечёткое выравнивание растягивало такую цитату через соседние элементы или обрезало её.

LE-3A разделяет две вещи:
- **доказательство** — диапазон, вырезанный кодом из проверенного снимка: символы, регистр и пунктуация сохраняются, нормализации нет;
- **утверждение** — новая формулировка, которая ссылается на одно или несколько доказательств по ID и цитатой не является.

Несмежные части (вводная и элемент) остаются двумя доказательствами и никогда не сливаются в одну «цитату». Дословность утверждения не проверяется и не требуется. Проверяется только, что каждая ссылка — существующий ID с той же ролью. Смысловую верность оценивает будущий шаг 1.5.

### Контракты

**Снимок.** Фрагмент и карта строк LE-2 проверяются заново: SHA-256 фрагмента, границы и повторный вывод карты строк. `snapshot_id` — хеш значимых полей карты: `source_id`, SHA-256 TXT и фрагмента, границы, строки. Время создания карты в идентичность не входит.

**Evidence** (`llm-wiki-memory/le3a-evidence/v1`):
- поля: `evidence_id`, `snapshot_id`, `source_id`, `excerpt_sha256`, `line_id`, `point`, `[start, end)` во фрагменте, `whole_line`, `[full_txt_start, full_txt_end)` (с учётом BOM как символа 0), `text_sha256`, `chars`;
- `evidence_id = "ev-" + sha256([контракт, snapshot_id, start, end])[:20]`; роль, утверждение и толкование в ID не входят;
- допустимы вся строка или непустой поддиапазон одной строки. `\n` внутрь не попадает, диапазоны через несколько строк не поддерживаются (отдельное будущее решение);
- текст не хранится: он каждый раз вырезается из снимка, а при загрузке запись должна полностью воспроизвестись (ID, границы, хеш, без лишних полей);
- `--full-txt` дополнительно сверяет срезы полного TXT.

**Манифест выбора** (`llm-wiki-memory/le3a-selection/v1`, частный):
- строки или поддиапазоны с ролями;
- неразрешённые зависимости: вид `UNRESOLVED_REFERENCE` / `OUT_OF_EXCERPT` / `NOT_SEARCHED`, строка и примечание. Примечание — только код `[A-Z][A-Z0-9_]*`, потому что оно попадает в пакет и в промпт.

**ContextPackage** (`llm-wiki-memory/le3a-context/v1`):
- роли: `TARGET`, `SHARED_CONTEXT`, `POTENTIAL_LIMITATION`, `POTENTIAL_EXCEPTION`, `UNRESOLVED_REFERENCE`;
- ровно одна цель; без дублей, конфликтов ролей и перекрытий; не более 12 доказательств, 8000 символов и 12 зависимостей; один снимок;
- `context_completeness` всегда `NOT_ESTABLISHED`; статусы `UNVERIFIED` / `REVIEW_REQUIRED`;
- `derived_links` строятся детерминированным разбором отсылок LE-2 и содержат только ID строк и номера, без текста отсылок:
  - какие строки ссылаются на строку цели и включены ли они;
  - на какие пункты ссылается цель и какие их строки не включены;
  - отсылки включённых строк за пределы фрагмента;
  - строки, не включённые и не связанные с целью.

  Связь — кандидат зависимости, а не доказательство её юридического действия. При загрузке пакета (`claim-request`, `claim-check`) `derived_links` заново не вычисляются и не проверяются: это сохранённая диагностика сборки, а не проверенные факты. Ни промпт, ни проверка ответа их не используют;
- `context_package_id` — хеш содержимого. В файле пакета нет текста и времени, поэтому одинаковый вход даёт побайтно одинаковый файл.
- при загрузке, кроме хеша пакета, независимо проверяются:
  - каждое доказательство: заново вырезается из снимка;
  - каждый `dependency_id`: пересчитывается по правилу сборщика;
  - поле `limits`: ключи, типы и значения должны совпадать с `PACKAGE_LIMITS` реализации.

**Запрос Claim Construction** (`llm-wiki-memory/le3a-claim-request/v1`):
- тело Chat Completions (`messages`, `json_object`, `max_tokens` 4096) с `transport: NOT_SENT` и `model: null`;
- тексты доказательств вырезаются из снимка заново и помечаются ID и ролями;
- инструкция требует сохранять модальность, субъект, область применения, отрицания, сроки, условия и исключения. Она запрещает выдумывать нормы и опираться на знания модели, а текст источника объявляет данными, не инструкциями.

**Ответ** (`llm-wiki-memory/le3a-claim/v1`):
- `claims[]` с полями `context_package_id`, `snapshot_id`, `source_id`, `statement`, `evidence[{evidence_id, role}]`, `conditions[]` / `exceptions[]` (`statement` + `evidence_ids`), `unresolved_dependencies` (ID зависимостей пакета), `legal_status: UNVERIFIED`, `review_status: REVIEW_REQUIRED`;
- любая ошибка отклоняет ответ целиком: строгий JSON без Markdown и повторных ключей, точный набор полей, пределы, неизвестный или повторный ID, несовпадение роли с пакетом, отсутствие цели, повторяющиеся утверждения (одинаковый `candidate_id`). Семантически близкие, но различные формулировки дублями не считаются;
- `exceptions` могут опираться только на `POTENTIAL_*`, а ссылки оговорок должны входить в `evidence` утверждения;
- принятое утверждение получает вердикты `structure: VALID`, `evidence_references: RESOLVED_TO_SOURCE_SPANS`, `legal_fidelity: NOT_VERIFIED`. Неразрешённые зависимости пакета переносятся в результат всегда; не отмеченные моделью перечисляются отдельно. Отчёт `claim-check` хранит только ID, число символов и вердикты, без текста утверждений. Полный частный результат добавлен в LE-3B.1 (`--full-result`, см. ниже).

1. `--max-tokens` обязан быть равен `claims.MAX_TOKENS` (4096). Это подтверждение, а не настройка: значение не повышается и не подстраивается.
2. Снимок и пакет перепроверяются как в LE-3A. ID пакета должен совпасть с `--expect-context-package-id`.
3. Запрос строится заново из пакета и снимка. Файл `--request` сравнивается с ним целиком в каноническом JSON, а не только по `body_sha256`: `4096.0` или `true` вместо целого — расхождение. `body_sha256` должен совпасть с `--expect-body-sha256`.
4. Тело POST: `{"model": <--model>, "messages": [system, user], "stream": false, "max_tokens": 4096, "response_format": {"type": "json_object"}}`. `payload_sha256` считается по тем же байтам, которые сериализует `http_transport` LE-1.
5. Режим:
   - `--replay <обмен>` — файл обмена должен совпасть по пакету, `body_sha256`, `payload_sha256` и модели, и ответ воспроизводится один раз без сети. При `transport_outcome: ok` целый HTTP-статус обязателен: подстановки 200 нет. Заглушка повторно сверяет привязку. `--endpoint`, `--post-ledger` и `--timeout` в этом режиме запрещены.
   - `--preflight` — проверяет условия live-вызова и печатает только ID, хеши, размеры, бюджет, счётчик журнала и наличие ключа. Ничего не пишет и не отправляет. Проверяются:
     - адрес: только частный или loopback IP, без DNS-имени, учётных данных и параметров;
     - модель;
     - тайм-аут 1–300 с;
     - журнал;
     - `count == --expect-ledger-count` и `count + 1 ≤ --post-cap`.
   - `--live` — после тех же проверок:
     1. audit hook разрешает соединение только с проверенным IP:портом;
     2. строка `post` записывается в журнал до отправки;
     3. выполняется ровно один POST через `http_transport` LE-1: без прокси, перенаправлений и повторов, ключ только из `LLM_WIKI_API_KEY`;
     4. пишется файл обмена;
     5. проверяются оболочка и утверждения.
6. Оболочка ответа:
   - размер не больше 262 144 байт до декодирования (`MAX_ENVELOPE_BYTES`, в него входит `reasoning_content`);
   - строгий UTF-8 и строгий JSON;
   - HTTP ровно 200;
   - затем `completion_content` из `llm_wiki.llm`: ровно один `choice`, роль `assistant`, `finish_reason=stop`, нет `refusal` / `tool_calls` / `function_call`, непустой `content`.

   `finish_reason=length` — отказ без частичного приёма. `finish_reason` любого типа JSON (массив, объект, число, логическое значение, неизвестная строка) не вызывает исключения: решение принимает `completion_content`, а в диагностику пишется `OTHER`.
7. Повторов, продолжения, чанкинга, запасной модели, подстройки бюджета и параллельных вызовов нет.

Итог `claim-run`:
- `ACCEPTED_AS_CANDIDATES` — код 0;
- `REJECTED`, `ENVELOPE_REJECTED` или `TRANSPORT_FAILED` — код 1;
- отказ до отправки — «Отказ: …» в stderr, код 1, без файлов.

В stdout выводятся только статусы, коды, счётчики, ID, SHA-256 и имена файлов. Адрес, модель, ключ и тексты не выводятся. При внутренней ошибке печатается только имя типа исключения.

### Журнал POST для `claim-run`

- Резервирование (`claim_run.reserve_post`):
  1. открытие с `O_NOFOLLOW`;
  2. `fstat`: обычный файл, права 0600, владелец — текущий пользователь;
  3. `flock(LOCK_EX)`;
  4. строгий подсчёт;
  5. проверка ожидаемого count и предела;
  6. запись строки `post` и `fsync`;
  7. снятие блокировки;
  8. только затем отправка.

  Следующий процесс уже видит новую строку, поэтому одновременные запуски не обходят предел.
- Тайм-аут, обрыв или аварийное завершение после записи строки расходуют бюджет.
- Ошибка записи — отказ без отправки.
- Частично записанная строка делает журнал непригодным: дальнейшие запуски отказывают, пока владелец не разберёт журнал вручную.
- Формат проверяется строго:
  - первая строка — `{"kind": "baseline", "count": N}` с целым N ≥ 0, прочие поля допускаются;
  - дальше только строки `{"kind": "post", …}`;
  - каждая строка завершается `\n`;
  - каждая строка — строгий JSON: повторные ключи на любой глубине (например, `{"count": 9, "count": 0}`) и `NaN` / `Infinity` — отказ, а не последнее значение.

  **Совместимость с реальным журналом LE-2 в этом этапе не проверялась** (его чтение было запрещено) — это шаг preflight оператора.
- `_ledgered` LE-2 не менялся: у него остаётся гонка «проверка, затем запись» без блокировки. Не запускать `run` LE-2 одновременно с `claim-run`. `flock` надёжен только на локальной ФС.
- Остаток бюджета — не разрешение. `--expect-ledger-count` требует, чтобы владелец посмотрел журнал непосредственно перед запуском. Исторические строки нельзя ни создавать, ни менять.

### Запуск (офлайн)

```bash
# Запрос для просмотра владельцем (как в LE-3A).
unshare -rn runtime/venvs/langextract/bin/python -m experiments.langextract_real claim-request <фрагмент> \
  --source-map <карта> --context <пакет> --output-dir <каталог>
# Воспроизведение частного файла обмена без сети.
unshare -rn ... claim-run <фрагмент> --source-map <карта> --context <пакет> --request <запрос> \
  --expect-context-package-id <ctx-…> --expect-body-sha256 <sha256> --max-tokens 4096 --model <ID> \
  --replay <обмен.json> --output-dir <каталог>
# Проверка условий live-вызова без сети и без записи.
unshare -rn ... claim-run <те же аргументы без --replay> --preflight --endpoint <частный URL /v1> \
  --post-ledger <журнал> --post-cap <N> --expect-ledger-count <M> --timeout <1–300> --output-dir <каталог>
# Полный результат из локального ответа модельной формы (привязка запроса NOT_ESTABLISHED).
unshare -rn ... claim-check <фрагмент> --source-map <карта> --context <пакет> --response <JSON> \
  --full-result --output-dir <каталог>
```

**`--live` нельзя запускать под `unshare -rn`.** В пустом сетевом пространстве соединение не установится уже после записи строки в журнал: итог будет `TRANSPORT_FAILED`, а разрешённый POST — израсходован. Под `unshare -rn` можно запускать `--preflight` и `--replay`.

`--preflight` не загружает LangExtract. `--replay` и `--live` лениво загружают транспорт LE-1, а вместе с ним LangExtract и urllib3. При импорте urllib3 создаёт сокет и привязывает его к `('::1', 0)`, чтобы проверить поддержку IPv6. Соединения, DNS и передачи данных при этом нет, а audit hook проекта такую привязку не блокирует.

### Известные риски и ограничения

- `max_tokens` 4096 не проверен и, вероятно, мал для GPT-OSS с рассуждением (см. п. 4).
- Точная привязка к доказательствам не означает, что утверждение из них следует.
- `context_completeness` всегда `NOT_ESTABLISHED`.
- Роли и `derived_links` по смыслу не проверены.
- Хеши не аутентифицируют данные:
  - внутренне согласованная подделка пакета, запроса и файла обмена при новых ожиданиях владельца проходит;
  - подменённый ответ с верной привязкой в файле обмена тоже проходит.

  Защита — закреплённые владельцем ID и хеши и права доступа к `runtime/`.
- Редакция источника не подтверждена: актуальность закреплённого RTF и его соответствие официальной действующей редакции не проверялись.
- Время ответа модели: LE-2A ждал 117,9 с при конкурентной нагрузке сервера. Тайм-аут и обрыв расходуют POST.
- Учёт POST:
  - у `_ledgered` LE-2 нет блокировки;
  - совместимость строгого разбора с реальным журналом не проверена;
  - `flock` надёжен только на локальной ФС.
- HTTP внутри LAN не шифрует ни текст источника, ни ключ API.
- Ветка CLI `--live` не исполнялась: создание `http_transport`, `NetworkGuard` с разрешённым адресом, вложенная функция `reserve` в `run_claim` и запись файла обмена. Резервирование журнала, однократная отправка и обработка ответа проверены только вызовом тех же функций с заглушкой транспорта.

### Исправления после ревью LE-3B.1

- **HIGH, журнал POST.** `ledger_count` разбирал строки обычным `json.loads`, который при повторном ключе молча берёт последнее значение: `{"kind": "baseline", "count": 9, "count": 0}` давало count 0 вместо отказа. Теперь используются `_unique_object` и `_reject_constant` из `llm_wiki.validation`, как в `parse_json`, но без его предела размера ответа: для журнала действует свой предел 1 МиБ.
